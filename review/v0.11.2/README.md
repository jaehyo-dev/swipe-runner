# v0.11.2 확인 기록 — 성능 표시를 설정으로, 휴대폰 음악 지지직거림

도구: `shots.mjs`(화면), `audio_probe.mjs`(오디오 그래프 조사). 헤드리스 크롬 + 맥 Metal GPU, 휴대폰 흉내 390x844 배율 3 터치. 실기기(아이폰) 측정은 불가.

## 1. 세 번 탭이 안 된 까닭 (아이폰 15 Pro 크롬)
- 크롬 휴대폰 흉내에서는 세 번 탭이 된다(v0.11.1 `overlay_menu.png`). 그러니 원인은 자리·동작 쪽으로 본다(실기기 미확인)
- 탭 자리는 "왼쪽 위 구석"이 아니라 일시정지·집 버튼 **오른쪽 옆**의 보이지 않는 150x124 칸(아이폰에서 약 81x67pt). 구석을 누르면 버튼이 눌린다 → 가장 그럴듯한 원인
- 탭 사이 0.4초 안 세 번: 손가락으로 빠르게 세 번이 어렵고, iOS는 빠른 연속 탭을 확대 동작으로 먼저 해석하려 한다(dblclick·gesturestart는 막아 둠, touch-action none)
- 이벤트 순서 문제는 아닐 것: Godot은 `_input`을 GUI(버튼)보다 먼저 부르고, 크롬 흉내에서 된다
- 처리: 설정 PERFORMANCE가 기본 방법. 세 번 탭·F3은 그대로 두고 같은 설정을 바꾼다(저장)

## 2. 음악 지지직거림 원인 조사
| 항목 | 결과 |
|---|---|
| 표본율 | 엔진은 웹에서 브라우저 기본값을 쓴다(`mix_rate.web = 0`) → 아이폰 48kHz. 음악 버퍼도 그 값으로 만들어 브라우저 변환 없음. 효과음 파일만 44.1kHz(소리 하나마다 브라우저가 변환) |
| 음악 재생 | Web Audio 버퍼 노드 = 오디오 스레드. 메인 스레드(프레임·디코딩)가 밀려도 음악은 끊기지 않는 구조 |
| CPU 4배 느리게 (`audio/x4.json`) | 20초 플레이(0.35초마다 스와이프 효과음)에서 출력 시계 밀림(끊김 추정) 0회. 1배(`x1.json`)도 0회. 크롬은 CPU 느리게가 오디오 스레드에 걸리지 않아 **메인 스레드 → 끊김은 재현되지 않음** |
| 오디오 스레드에서 도는 JS | 엔진 믹서 워클릿 1개(소리는 없음) + **효과음마다 위치 보고 워클릿**(128표본마다 메시지, 소리 하나당 초당 375개). 워클릿 메시지 합계 초당 480개 |
| 결론(추정) | 프레임 끊김·곡 디코딩과 같은 때가 아니라 **효과음이 몰릴 때** 오디오 스레드 JS·메시지(WebKit 워클릿)가 밀려 버퍼가 비는 것이 가장 그럴듯하다. 실기기에서 성능 표시 GAP으로 확인 필요 |

## 3. 고친 것 / 하지 않은 것
- 효과음 위치 워클릿 → 빈 노드(`export_presets.cfg` head_include). 게임은 효과음 재생 위치를 쓰지 않는다. 후(`after4.json`): 위치 워클릿 0개, 메시지 480 → 381/초(엔진 믹서 몫만), 오류 0
- 휴대폰만 출력 버퍼 latencyHint 0.02: 크롬 흉내 baseLatency 5.3 → 21.3ms. 브라우저가 알려 주는 값이라 `position()`이 빼므로 박이 그대로. WebKit이 이 값을 알려 주지 않아도 늘어난 몫은 약 16ms(20ms 이하). currentTime 계단 최대 37 → 43ms는 v0.11.1 시계 보간 테스트 범위(43ms) 안
- 하지 않음: 48kHz 변환(음악은 이미 48kHz로 풀고, 원인 후보가 아님 — 효과음 변환 비용은 작다), 디코딩 시점 옮기기(다음 곡 구간이 판 진행에 따라 정해져 미리 풀 수 없고, 메인 스레드는 음악 끊김 원인이 아님), 효과음 동시 수 상한은 그대로(일반 6 + 방울 3 + PERFECT 2 = 최대 11, 방울 0.06초 묶기 유지)
- 성능 표시 오디오 줄: 출력 표본율, 출력 지연(baseLatency + outputLatency), 최근 10초 끊김 추정(`AudioGapMeter`: 0.5초 묶음 최댓값 기준 오디오 출력 시계가 15ms 넘게 밀린 횟수, 일시정지 사이는 셈하지 않음, 웹만)
