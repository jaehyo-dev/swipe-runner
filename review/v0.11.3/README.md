# v0.11.3 확인 기록 — 일시정지 뒤 음악·효과음 밀림, 휴대폰 디코딩 시점

도구: `pause_probe.mjs`(창 없는 헤드리스). 크롬 = 휴대폰 흉내 390x844 터치, WebKit = 플레이라이트 WebKit(맥) 아이폰 흉내 + 방향키.
옛 = 배포된 v0.11.2, 새 = 이 버전 로컬 빌드. 결과 원본 `probe/*.json`. **아이폰 실기기 측정은 못 함.**

## 1. 원인 (조사)
| 항목 | 옛 방식 (v0.11.2) | 결과 |
|---|---|---|
| 재개 때 기준점 | AudioContext `suspend()` → `resume()`. 음악 시계(currentTime)가 같이 서서 기준점(t0)은 그대로 | 아이폰 WebKit은 깨어날 때 출력 경로를 다시 열어 실제 출력 지연이 바뀔 수 있는데, 게임은 브라우저가 알려 주는 지연만 뺀다 → 그만큼 소리가 화면보다 밀린다(실기기 확인 불가, 가장 그럴듯한 원인) |
| 깨어난 직후 | 오디오가 몇~수십 ms 늦게 돌고 그동안 화면 시계가 기다렸다 따라감 | 크롬에서도 이어 한 직후 박자 오차 최소 −85~−110ms (아래 표) |
| 효과음 | 엔진이 트리 일시정지 때 효과음을 "멈춤"으로 두었다가 재개 때 남은 꼬리를 다시 튼다 | 일시정지 직전 입력의 소리가 3·2·1 뒤 입력 없이 늦게 들림 |
| 효과음 예약 | 엔진 효과음은 `start(0)`(지금 바로). 박 기준 예약 없음 | 측정에서 명령 → 소리 예약 0ms (옛·새 모두) |
| 탭 숨김 | 같은 경로(pause → suspend) | 같은 결과 |

## 2. 고친 것
- 웹 일시정지는 AudioContext를 재우지 않는다. 곡 노드만 세우고 **화면이 멈춘 음악 시간**의 곡 위치를 기억 → 이어 하기 때 그 위치부터 `start(R, 위치)`로 예약, 기준점 t0·곡 경계·반복 끄기 시각을 같은 만큼 옮김 (`web_music.gd` JS `hold`/`resumeIn`)
- 3·2·1은 오디오 시계(들리는 시각)로 센다: 숫자 끝 = 음악이 다시 들림 = 판정 재개. 오디오 시계가 1초 넘게 서 있으면 실제 시간으로 끝낸다
- 일시정지 때 효과음 재생기를 모두 끈다(멈춤 상태로 두지 않음)
- 자동 테스트: `tools/test_web_music.py`(가짜 AudioContext: 이어 한 위치 = 멈춘 위치, 경계 함께 밀림, 숫자 세는 중 다시 멈춤, 10번 반복 누적 0, 화면 시간으로 멈춤), `tests/test_audio.gd`(효과음 꺼짐, 디코딩 시간 규칙)

## 3. 박자 오차 (화면 음악 시간 − 게임이 아는 소리 위치, ms)
"시작"은 판 시작 0.5초 뒤 3초(일시정지 전 기준값). 헤드리스는 음악 시계가 계단처럼 올라 화면 시계가 늘 약 −15ms 뒤에 있다(일시정지와 무관).

| 경우 | 시작 평균 / 최소 | 이어 한 뒤 평균 | 이어 한 뒤 최소(가장 나쁜 프레임) |
|---|---|---|---|
| 옛 크롬 일시정지 10번 | (없음) | −8.8 ~ −21.5 | **−84.8 ~ −102.7** |
| 새 크롬 일시정지 10번 | −16.2 / −28.9 | −17.2 ~ −19.7 | −30.2 ~ −41.5 |
| 옛 크롬 탭 숨김 5번 | (없음) | −10.8 ~ −16.9 | **−93.4 ~ −109.7** |
| 새 크롬 탭 숨김 5번 | −16.5 / −28.5 | −16.1 ~ −22.4 | −31.7 ~ −44.0 |
| 옛 WebKit 일시정지 | (없음) | −13.5 ~ −17.5 | −17.7 ~ −23.1 |
| 새 WebKit 일시정지 10번 | −14.6 / −20.1 | −14.8 ~ −20.6 | −18.9 ~ −34.3 |
| 옛 WebKit 탭 숨김 | (없음) | 한 번 +37(최대 +515) | −22.8 ~ −41.8 |
| 새 WebKit 탭 숨김 5번 | −14.6 / −54.6 | −14.6 ~ −17.9 | −18.4 ~ −54.6(시작에도 같은 값) |

- 기준값 대비 평균 차이 최대 약 6ms, 반복해도 커지지 않음(10번 동안 추세 없음) → 목표(20ms 이하, 누적 없음) 안
- 옛 방식의 이어 한 직후 −85~−110ms 밀림이 사라짐(크롬). 맥 WebKit은 옛 방식도 크지 않아 아이폰 증상은 재현되지 않음
- 탭 숨김에서 한 프레임 +430~+515ms가 옛 WebKit 1번, 새 크롬 첫 측정 1번(재측정 5번은 없음) 나왔다. 흉내 도구가 AudioContext를 강제로 재우는 시점과 겹친 것으로 보이나 원인 미확정

## 4. 출력 지연과 효과음
| 경우 | 실제 출력 지연 − 알려 준 지연 (전 → 후) | 입력 → 효과음 (전 → 후, 평균) |
|---|---|---|
| 크롬(옛·새) | −10.7 → −10.7ms (바뀌지 않음) | 약 133 → 132ms (= 입력 → 명령 약 50ms + 출력 약 83ms, 헤드리스 가짜 장치) |
| WebKit(옛·새) | 측정 불가(WebKit의 출력 타임스탬프가 지연을 담지 않음) | 약 7 → 7ms(명령까지, 키 입력). 알려 준 출력 지연 30.8ms(base 2.7 + output 28.1) |

- 재개 뒤 효과음 지연 차이: 모든 경우 10ms 이하, 반복 누적 없음. 효과음은 박 기준 예약 없이 바로 재생(예약 0ms)
- 처음부터(일시정지 없이) 늦게 들린다면: 휴대폰은 v0.11.2에서 출력 버퍼를 20ms로 늘렸다(latencyHint 0.02). 아이폰의 실제 값은 설정 PERFORMANCE의 오디오 줄 "출력 지연"으로 확인. 줄이는 방법은 latencyHint를 다시 줄이기(지지직거림과 맞바꿈)뿐이고, 엔진 효과음 경로(입력 다음 프레임에 재생)는 더 줄일 곳이 없다

## 5. 휴대폰 지지직 (가벼운 조치)
- 휴대폰 웹: 다음 곡 디코딩은 메인 화면·일시정지·숫자 세기·숨 고르기 마디에 프레임당 8ms, 보통 마디에서는 곡 예약 4초 전부터만 3ms. 메인 화면·게임 오버에서 다음 판의 첫 경계 곡을 미리 푼다(PC 웹도)
- 숨 고르기는 8마디에 한 번이고 곡 준비는 4마디마다 필요해서 숨 고르기만으로는 모자란다 → 급할 때 예외를 둠
- 출력 버퍼 늘리기는 v0.11.2의 20ms를 그대로 둔다(더 늘리면 WebKit이 알려 주지 않는 몫이 박자 오차 20ms를 넘을 수 있음)
- 하지 않음: 48kHz 변환 등 큰 작업 → PROGRESS.md "나중에(앱 출시 때)"
