# 자동 그래픽 낮추기 오작동 (v0.9.0)

v0.7.0 무렵부터 프레임이 멀쩡한데도(브라우저 프레임 99%가 16.8ms) 그래픽 단계가 내려갔다 (`review/v0.8.1/timing.md`, `review/v0.6.3/perf_mac.md`).

## 원인: 판단에 쓴 값이 브라우저 프레임이 아니었다
v0.8.2는 `main.gd _watch_frames()`가 **엔진 `_process` 안에서 `Time.get_ticks_usec()`로 잰 간격**을 2초씩 모아, 99% 값이 20ms를 넘으면 바로 한 단계 낮췄다.
v0.8.2를 그대로 둔 측정 빌드에 원인 기록 줄을 넣고(엔진 쪽 간격과 같은 2초의 브라우저 rAF 간격을 함께 찍음), RTX 4060으로 쟀다.

| 낮춘 시각 | 엔진 `_process` 간격: 99% / 위 5개 (ms) | 같은 2초의 브라우저 rAF: 99% / 위 5개 (ms) |
|---|---|---|
| 7.5초 (1단계) | **25.8** / 18.8, 20.1, 25.8, 26.1, 35.8 | **16.8** / 16.8 ×5 |
| 243.8초 (2단계) | 20.4 / 18.5, 18.5, 20.4, 20.7, 47.2 | 16.8 / 16.8 ×4, 33.4 |
| 259.8초 (3단계) | 21.7 / 18.3, 19.3, 21.7, 23.1, 37.6 | 16.8 / 16.8 ×4, 33.5 |
| 261.8초 (4단계) | 20.7 / 18.2, 18.8, 20.7, 24.1, 44.8 | 16.8 / 16.8 ×4, 33.4 |

- 화면에 실제로 그려진 프레임(rAF)은 16.8ms인데, 엔진 안에서 잰 간격은 18~36ms로 흔들렸다. 같은 프레임 안에서 `_process`가 불리는 시점이 앞 작업(웹 음악 디코딩 3ms 예산, 곡 예약 등)에 따라 앞뒤로 밀리기 때문으로 본다. 브라우저 프레임 하나가 33ms였던 순간도 엔진 쪽에서는 37~47ms로 부풀었다
- 2초에 느린 값 3개(99% 자리)면 바로 낮추는 기준이라 이 흔들림에 걸렸다
- 측정: v0.8.2, 100BPM부터 265초, 1710x925 × 2배, WSLg 창 + d3d12(RTX 4060). 같은 조건 160BPM 60초 1회는 낮춤 0 (맥에서는 같은 측정이 3.7초에 걸렸다)

## 고친 것
1. 웹에서는 **브라우저가 실제로 그린 프레임 간격**(requestAnimationFrame)으로 판단한다. JS가 간격을 모으고 엔진은 30프레임마다 한 번 가져간다 (`main.gd FRAMES_JS`, `_watch_frames`)
2. 기준 강화 (`scripts/logic/quality_guard.gd`, 자동 테스트 `tests/test_quality_guard.gd`)
   - 1초 구간의 99% 프레임이 20ms를 넘는 구간이 **3초 연속**일 때만 낮춘다. 한 번에 한 단계
   - 페이지를 연 뒤(가림막이 걷힌 뒤), 탭이 가려졌다 돌아온 뒤(0.25초 넘는 멈춤), 화면 전환(시작·다시 시작·메인 화면) 뒤, 단계를 낮춘 뒤 **5초**는 판단하지 않는다
   - 낮출 때마다 콘솔에 `QUALITY 단계 시각 이유`. 예: `QUALITY 1 22.3 99% 프레임 83.4, 83.4, 100.0 ms가 3초 연속 20ms 초과`

## 고친 뒤 측정 (프레임이 정상인 경우 낮춤 0회가 목표)
| 측정 | 방법 | 프레임 | 중앙값 | 99% | 최대 | 33ms 초과 | 자동 낮춤 |
|---|---|---|---|---|---|---|---|
| 100BPM부터 265초 | WSLg 창 + d3d12, 3420x1850 | 15897 | 16.7 | 16.8 | 116.8 | 14 | **0** |
| 160BPM 시작 60초 | WSLg 창 + d3d12, 3420x1850 | 3603 | 16.7 | 16.8 | 33.4 | 4 | **0** |
| (3회째는 사용자 요청 "측정 때 창을 띄우지 말 것"으로 멈춤) | | | | | | | |
| **160BPM 시작 60초 (1회)** | **Xvfb 가상 화면 + d3d12, 3420x1850, 창 없음** | 3606 | 16.7 | 16.8 | 83.3 | 3 | **0** |
| **100BPM부터 265초 (2회)** | 같음 | 15920 | 16.7 | 16.8 | 83.4 | 4 | **0** |
| **160BPM 시작 60초 (3회)** | 같음 | 3616 | 16.7 | 16.8 | 50.1 | 2 | **0** |
| 참고: 100BPM 265초 | 윈도우 크롬 헤드리스 + D3D11, 1710x926, 창 없음 | 37758 | 5.6 | 19.2 | 39.3 | 2 | 3단계 (223·248·265초) |
| 참고: 160BPM 60초 × 2 | 같음 | 6827 / 7235 | 7.4 / 7.2 | 20.6 / 20.6 | 20.8 | 0 | 3단계 / 2단계 |

- **판정 기준은 굵은 3회(Xvfb, 60Hz)**: 렌더러 `ANGLE (Microsoft Corporation, D3D12 (NVIDIA GeForce RTX 4060), OpenGL 4.6)`, 59.9~60fps, 낮춤 0회. 측정 빌드는 기록 직전 코드(음악 페이드 수정 전, 프레임과 무관)
- 윈도우 크롬 헤드리스(D3D11, RTX 4060)는 창 없이 GPU를 쓰지만 수직 동기가 없어 rAF가 60fps에 묶이지 않는다. 그리는 시간은 평소 5~7ms인데 간격이 정확히 20.6~20.7ms인 프레임이 간간이 몰려(헤드리스의 프레임 배달 방식으로 봄) 기준 20ms를 살짝 넘겨 낮췄다. 실제 60Hz 화면의 흐름이 아니라 판정에서 뺐다. 3420x1850 캔버스에서는 화면 밖 버퍼 복사로 27fps까지 떨어졌다
- 측정 방법(창 없이): `env -u WAYLAND_DISPLAY xvfb-run -a -s "-screen 0 1920x1080x24" node review/v0.9.0/measure_frames.mjs <주소> <결과> 1710x925` (WSL 기본). 윈도우 헤드리스는 `MEASURE_WIN=1`. 맥은 그대로 헤드리스 Metal

- 창 측정 265초의 116.8ms 같은 튐은 한 번씩이라 3초 연속 기준에 걸리지 않았다 (v0.8.2는 이런 튐 근처에서 2~4단계까지 내려갔다)
- 웹 확인(헤드리스 소프트웨어 렌더링, 진짜로 80~180ms 프레임)에서는 이유와 함께 1~2단계 낮췄다 (`check_web.json`의 logs): 정말 느릴 때는 그대로 동작한다
