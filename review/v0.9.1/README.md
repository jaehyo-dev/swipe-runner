# v0.9.1 확인 기록

측정은 모두 창 없이(WSL 데스크탑): GPU 측정은 Xvfb + d3d12(ANGLE D3D12 RTX 4060, 60Hz), 화면 캡처는 헤드리스 소프트웨어 렌더링.
서버는 GitHub Pages처럼 gzip + ETag + 10분 캐시(`serve_gzip.mjs`). 측정 횟수는 조건마다 2회.

못 맞춘 이유:
- 엔진 `index.wasm`이 gzip 9.9MB: Fast 4G(약 1MB/s)에서 이것만 약 10초, 와이파이(2.5MB/s)에서 약 4초. 줄이려면 엔진 직접 빌드가 필요(사용자 결정: 지금은 하지 않음)
- 받은 뒤 시작 준비 약 3.5초(두 번째 방문은 받는 것이 0인데도 3.4~4.1초): 엔진 켜기 약 1.5초 + 메인 화면 셰이더 준비. 이 PC의 GPU 경로(WSL d3d12 → GL 번역)는 셰이더 만들기가 느린 편이라 실제 기기와 다를 수 있다
- 음악 파일은 다시 줄이지 않았다: 첫 곡(430KB)만 메인 화면 전에 받으므로 줄여도 0.1초 안팎, 다시 만들려면 libvorbis가 든 ffmpeg가 필요(이 PC에 없음)하고 귀로 확인해야 한다
- 결과 파일: `load/before_*.json`, `load/after_*.json`, 로딩 화면 캡처 `load/loading_1s.png`, `load/loading_6s.png`

## 첫 판 끊김 (`measure_play.mjs`, GPU 60Hz)
메인 화면이 뜨자마자 시작(2단계 준비가 끝나기 전) → 준비를 마저 하느라 1.7~1.9초 뒤 시작 → 시작부터 12초: 720프레임, 33ms 넘는 프레임 0, p99 16.8ms, 최대 16.8ms (`play_gpu.json`)

## 일시정지 뒤 박자 오차 (`measure_play.mjs`, GPU, 4회)
화면 음악 시간 − 들리는 소리 위치(+면 화면이 앞섬), 이어 한 뒤 3초:
- 일시정지 없이 첫 판 1초 뒤 3초(기준선): 평균 −16.5ms (−23.0 ~ +1.4)
- 일시정지 → 3·2·1 → 이어 한 뒤: 평균 −17.0 ~ −17.4ms (−40.3 ~ −8.8)
- 평균은 기준선과 1ms 안으로 같다: 일시정지가 박을 어긋나게 하지 않는다(20ms 이하). 이어 한 직후 몇 프레임은 소리가 다시 흐르며 오디오 시계가 한 번에 올라 최대 약 −40ms(기준선 −23ms)까지 벌어졌다가 0.1초 안에 돌아온다
- 크롬 오디오 시계가 블록 단위 계단으로 올라 프레임마다의 차이에는 계단 크기가 섞인다(그래서 평균으로 본다). 평균 −17ms는 일시정지와 무관한 기존 값(화면 시간이 소리보다 약 한 프레임 늦음)
