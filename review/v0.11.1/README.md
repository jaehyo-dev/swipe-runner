# v0.11.1 확인 기록 — 점수 절반, 휴대폰 끊김, 성능 표시, GRAPHICS, 10000점 연출

캡처·측정: `phone_web.mjs` (창 없는 크롬 + 맥 M3 Metal GPU, 390x844, 배율 3, 터치). 음악 시계 표: `tools/clock_table.gd`. 점수 분포: `tools/score_report.gd`.

## 1. 원인 측정 (아이폰 15 Pro + 크롬 = WebKit)
실기기 측정은 불가. 맥 헤드리스는 아이폰 GPU·WebKit 오디오·120Hz 화면을 재현하지 못하므로 아래는 "숫자로 확인할 수 있는 원인"만이다.

| 항목 | 결과 |
|---|---|
| 배율 3의 실제 그리는 해상도 | 캔버스 1170x2532(390x844 × 3, 실기기 1179x2556). **고치기 전** 3D 배율 0.758 → 887x1920(170만 화소) + MSAA 4x + 젤리 화면 복사. **고친 뒤** 배율 2.0 상한 → 780x1688(132만 화소, −23%) + MSAA 2x(휴대폰). 실기기는 786x1704 (자동 테스트) |
| 120Hz rAF 간격 | 헤드리스는 60Hz만 나온다. iOS WebKit(크롬 앱 포함)은 기본 rAF 60Hz 제한, 저전력 모드 30Hz로 알려져 있다. 실제 값은 성능 표시의 Hz로 사용자가 확인 |
| WebKit 오디오 시계 | 실측 불가 → 흉내 표(`clock_before.md` → `clock_after.md`): 계단 10/21/43ms × 되돌림 20ms × 60/120Hz. **고치기 전** 이동량 흔들림 최대 22~29%, 43ms 계단 + 되돌림에서 세상이 멈췄다 튀는 프레임(193%). **고친 뒤** 멈춤 0, 흔들림 최대 7.4% (자동 테스트 `test_WebKit처럼_큰_계단과_되돌림에도_멈춤_없이_고르게`) |
| 가비지 수집 | JS 힙이 줄어든 프레임 수(12초 플레이). 전 2번(11.2MB, 음악 디코드 조각마다 새 배열) → 후 0번. 맥에서는 수집 프레임도 16.6ms라 끊김은 없었다 |

## 2. 프레임 표 (CPU 4배 느리게, ?bpm=160, 시작 뒤 12초, 불러오기는 느리게 하지 않음)
| | 프레임 | 중앙 | p99 | 최대 | 25ms 넘음 | 긴 작업 | GC |
|---|---|---|---|---|---|---|---|
| 전 v0.11.0 (배포본) 2회째 | 720 | 16.7 | 16.8 | 16.8 | 0 | 0 | 2 |
| 후 v0.11.1 2회째 | 720 | 16.7 | 16.8 | 16.8 | 0 | 0 | 0 |
| (1회째: 부하 평균 2.7~3.6, 버림) 전 / 후 | 717 / 701 | 16.7 | 16.8 / 33.4 | 150 / 50 | 5 / 14 | 0 / 1 | - |

2회째는 부하 평균 2.4~2.7에서 전 → 후 순서. 1회째는 다른 세션의 테스트가 겹쳐(부하 3.6~11) 기준 밖이라 표에만 남겼다. 결론: 맥 GPU에서는 전후 모두 60fps라 이 측정으로 끊김이 고쳐졌다고 말할 수 없다. 줄어든 것은 그리는 화소(−23%), MSAA(4x→2x), 시계 멈춤, GC다. **아이폰에서 직접 확인 필요.**

## 3. 매 프레임 새로 만드는 것 (찾은 것 → 처리)

## 리뷰
- architect(방향): 원인 순위(해상도·MSAA·화면 복사 > 시계 멈춤·점프 > 디코드 GC > 저전력 30Hz에서 자동 낮춤), 시계 수정, 배율 2.0, 휴대폰 MSAA 2x, 배열 재사용, 단계 순서 → 수용. "데드밴드(±SNAP 안에서 보정 안 함)"는 거절: 오차가 남아 박과 어긋남이 쌓인다 → 대신 천천히 메우고 프레임당 보정량 상한 8%
- Codex: `?points` 확인 값이 진짜 BEST·오늘의 판 기록에 저장됨 → 수용(그 창은 따로 쓰는 기록 파일)
- 내 리뷰: 웹에서 JS 참·거짓이 정수로 와 `== true`가 오류 → 고침(디버그 내보내기로 찾음)
